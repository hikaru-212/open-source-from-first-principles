# Contributing

Contributions are welcome when they help technically capable newcomers move toward contribution-ready understanding.

## Preserve the Educational Method

Contributions should:

- start from the physical problem;
- bound guarantees precisely and state non-guarantees;
- distinguish a project mechanism from application semantics;
- prefer authoritative upstream evidence;
- avoid terminology-first, encyclopedic expansion;
- keep the main learning path short;
- move advanced internals into clearly marked Deep Dive material.

## Technical Corrections

Technical corrections should ideally include an authoritative upstream reference, such as:

- official documentation;
- Javadoc or API documentation;
- project source code or tests;
- design proposals or KIPs where relevant.

When reporting a problem, separate the observed behavior from the suspected cause and identify the technical baseline to which the correction applies.

## Scope and Licensing

Keep each contribution small, coherent, and reviewable. Avoid unrelated rewrites or adding advanced material to the main path without a clear teaching need.

Documentation and educational prose are contributed under CC BY 4.0. Software and substantial standalone executable examples are contributed under Apache-2.0. See [LICENSE-CONTENT.md](LICENSE-CONTENT.md) for the boundary.
